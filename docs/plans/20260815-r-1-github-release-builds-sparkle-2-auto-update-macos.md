# R-1: GitHub release builds + Sparkle 2 auto-update (macOS)

## Overview

Pushing a `v*` tag runs the CI gate, archives an ad-hoc-signed macOS app, signs it
with Sparkle's EdDSA key and publishes a GitHub Release carrying a
symlink-preserving zip plus a signed `appcast.xml`. The shipped app embeds
Sparkle 2, a stable `releases/latest/download/appcast.xml` feed URL and the
public half of the signing key, and offers updates through Sparkle's own UI.

Two technical questions the ticket flags as open were resolved experimentally
before writing this plan, and their answers are load-bearing here:

1. **Per-destination linking works.** A scratch XcodeGen project (multiplatform
   target, `supportedDestinations: [macOS, iOS]`) with
   `destinationFilters: [macOS]` on a package-product dependency emits
   `platformFilters = (macos, )` on the `PBXBuildFile`; `generic/platform=iOS`
   builds green with Sparkle in the graph, and the macOS build embeds
   `Sparkle.framework` automatically. The standing note in `project.yml` and
   `CLAUDE.md` that package-product dependencies "cannot be per-destination
   filtered through XcodeGen" is wrong and is corrected by this plan. Whether
   SwiftTerm/libgit2 should also get filters is noted as follow-up, not done.
2. **Sparkle 2.9.5** (`sparkle-project/Sparkle`, revision
   `79bc9e872948e47877e76f194cb0c8e0412b0b90`) is a SwiftPM `binaryTarget`
   package declaring `platforms: [.macOS(.v10_13)]`. It resolves into
   `Package.resolved` as an ordinary v2 remote pin (`version` 2.9.5 +
   revision), so `DependencyPinTests` and `LicenseCoverageTests` need no new
   mechanism. Its `LICENSE` already carries an `EXTERNAL LICENSES` section
   (bsdiff/Colin Percival, sais/Yuta Mori, pdqsort/Orson Peters, Mark Hamlin),
   so unlike libgit2 the verbatim copy is the whole obligation — but that fact
   gets pinned by a test, because "checked and found clean" must not be
   indistinguishable from "nobody looked".

Per the answered question, the EdDSA **public key ships as a clearly-marked
placeholder**: `swift test` asserts only that `SUPublicEDKey` is well-formed
(44-char base64 decoding to 32 bytes), and the release workflow refuses to run
while the placeholder value is still in the plist. Generating the real pair and
swapping it in is a documented one-time manual step.

## Development Approach

- **Testing approach**: Regular (code first, then tests). Everything new here is
  either configuration or view-layer glue; the tests are static assertions over
  repository files, the pattern `ReleaseMetadataTests`/`DependencyPinTests`
  already establish.
- No logic goes into `PisakaCore`: Sparkle is configuration, not a decision, and
  Core stays Foundation-only. All Sparkle-touching source is under
  `#if os(macOS)`.
- Complete each task fully before moving to the next.
- **CRITICAL: every task MUST include new/updated tests.**
- **CRITICAL: `swift test` must pass before starting the next task**; tasks that
  touch `project.yml` additionally run both destination builds.
