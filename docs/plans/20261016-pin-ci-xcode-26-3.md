# Pin CI and the release workflow to Xcode 26.3, and run the local app-layer gates on the pinned toolchain

## Overview

CI and the release workflow are pinned to Xcode 16.4 in five `setup-xcode` steps. Development happens on Xcode 27.1, so no local gate could see the `.commands { }` eleven-entry failure. This plan does four things:

- Moves all five pins to Xcode 26.3, keeping the runner label `macos-15`.
- Makes the five pins one tested value that `docs/RELEASING.md`, the `Makefile` and `CLAUDE.md` are each checked against.
- Runs every `xcodebuild` the Makefile issues under that toolchain through `DEVELOPER_DIR`, refusing when it is missing.
- Re-establishes two toolchain-dependent facts for 26.3: the `Package.resolved` schema behaviour and the `CommandsBuilder` entry ceiling.

Only Xcode 27.1 is installed on the development machine. Both 26.3 facts are therefore established from the PR's CI run, which is the only environment with Xcode 26.3, and no task assumes a local 26.3:

- The `Package.resolved` behaviour gets a permanent guard step in `build-macos`.
- The `CommandsBuilder` ceiling is read off the 26.3 SDK's SwiftUI `swiftinterface` by a one-off CI step that is removed before merge.
- The observed values are written into the docs in Post-Completion.

This ticket touches no file under `Sources/`.

## Development Approach

- **Testing approach**: TDD for the pin rules. Each new assertion is written first against the current 16.4 tree. It must go red there, or green only once the bump lands, for the reason its message gives. Then the change makes it green.
- Complete each task fully before moving to the next.
- Mutation-check every new rule by hand before the task closes: change one of the five values, the RELEASING.md version, the Makefile default, or one CLAUDE.md prefix, and confirm the suite fails. Then revert.
- One authority, stated once in the shared helper's doc comment. The authority is the set of `xcode-version:` values across both workflows, which must be exactly one value. RELEASING.md, the Makefile default and the CLAUDE.md prefixes are each asserted equal to it.
- No task assumes `/Applications/Xcode_26.3.app` exists locally. The Makefile's refusal path is the one exercised here.
- **CRITICAL: every task MUST include new/updated tests**
- **CRITICAL: all tests must pass before starting next task**

## Post-Completion

These steps need the PR's CI run, the only environment with Xcode 26.3. They are done by hand or by the reviewer, not as task checkboxes.

- Push the branch and open the PR. All four jobs must pass: `test`, `lint`, `build-macos` (app tests, Release build, launch smoke test) and `build-ios`.
- Record the guard step's result.
  - It passes: Xcode 26.3 left the committed v2 file alone on a fresh clone with an unchanged pin set. Complete `DependencyPinTests`' doc comment with that observation.
  - It fails: record the observed rewrite, and re-emit the values in v2 as the comment instructs.
  - Note whether the SPM cache hit on that run. Its key does not include the Xcode version.
- Read the temporary probe's log. Write the `CommandsBuilder` limit for Xcode 26.3 into `app-shell.md`'s paragraph: the number of `buildBlock` children, or "no fixed ceiling" if `buildPartialBlock` is declared.
- Remove the temporary probe step, then push.
  - Confirm `grep -n "TEMPORARY" .github/workflows/ci.yml` is empty.
  - Confirm CI is green again on the final commit.
- The release workflow cannot run without a tag. Its shape is covered by `ReleaseWorkflowTests`, and its `test` job's pin is in the same assertion as `ci.yml`'s.
- Human step, out of scope: install Xcode 26.3 at `/Applications/Xcode_26.3.app` on the development machine. Until then, `make test-app` / `make build` refuse, or run under an explicit `PINNED_XCODE=` override.
