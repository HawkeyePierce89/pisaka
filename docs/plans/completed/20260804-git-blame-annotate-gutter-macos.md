# Git Blame — Annotate Column in the Editor Gutter (macOS)

## Overview

JetBrains-style "Annotate with Git Blame": a right-click on the editor gutter toggles a permanent column to the left of the line numbers showing, per line, who last changed it and when. Blame is computed against the **worktree** file (`git blame --porcelain`), so it matches what the user sees given autosave. All the logic — the value type, the porcelain parser, and the edit-driven shift of the annotation array — is pure Foundation in `PisakaCore` under tests; the view layer (a thin `BlameController` plus an annotation column inside the existing `LineNumberRulerView`) stays untested per repo convention. macOS only; iOS has no gutter.

## Design decisions (to be captured in doc comments)

**Porcelain over line-porcelain.** `git blame --porcelain` is chosen deliberately: commit metadata appears once per commit and later lines of the same commit carry only the hash, so the parser keeps a `hash → metadata` table. The output is a fraction of `--line-porcelain`'s size, which matters for the megabyte-scale files the ticket worries about; the table costs ~10 lines. The choice is pinned by a test that feeds a repeated commit with no metadata block.

**`BlameLine`.** `public struct BlameLine: Equatable` — `hash`, `author`, `date` (raw ISO-8601 string, `Commit.date`'s convention), `summary`, and a computed `isUncommitted` (`hash` is all zeros — what worktree blame emits for lines not yet committed). The parser returns `[BlameLine?]`, one entry per file line in final-line order; `nil` means "no data for this line" (a gap in truncated output, or a line inserted after the load). `nil` and `isUncommitted` are both drawn blank, but they are different facts and stay distinct in the model.

**The TAB rule — content is recognized before anything else.** In `--porcelain` each blamed line's *own source text* is emitted on its own line prefixed with a single TAB (`\t`). That prefix is the only thing separating file content from the metadata grammar, and the grammar is otherwise trivially forgeable by ordinary source code: a Swift line reading `author Evil <x@y>` or a fixture containing `0000000000000000000000000000000000000000 1 2 3` is, byte for byte, a valid `author` field or a valid group header. So the parse loop's **first** test on every line is `hasPrefix("\t")` — such a line is consumed as content (it closes the current group's metadata block and is otherwise ignored) and **never reaches the header or field matching**. Getting this order wrong does not crash; it silently rewrites an author, or invents a whole group at a bogus line number, from the file's own text — which is why it is stated as a rule rather than left implicit, and why the fixtures below include source lines spelled exactly like a header, an `author`, a `boundary` and a `previous`.

**Header grammar actually handled.** A group header is `<40-hex sha> <orig-line> <final-line> [<num-lines>]`; entries are placed by the **final line number**. Between headers come the field lines, of which the parser reads `author`, `author-time`, `author-tz` and `summary`. Every other field is skipped by falling off the end of the switch, and that deliberately covers the two valueless/extra ones git actually emits: **`boundary`** (a lone keyword line, no value, for a commit at the boundary of the traversal) and **`previous <sha> <path>`** (the parent commit and the file's path there). Both are ignored rather than special-cased — they carry nothing the column shows — but they are pinned by fixtures because both are shapes a naive "first token, rest is value" split can mis-handle (`boundary` has no value at all, `previous` starts with a 40-hex-looking second token).

**Date synthesis.** Porcelain gives `author-time <epoch>` + `author-tz <+0300>`, not an ISO string. The parser synthesizes `2026-08-04T19:55:07+03:00` (the exact shape `%aI` produces, so `BlameLine.date` and `Commit.date` are interchangeable to a formatter): a fixed `DateFormatter` (`en_US_POSIX`, `yyyy-MM-dd'T'HH:mm:ss`, `TimeZone(secondsFromGMT:)` from the parsed offset) plus the offset re-spelled with a colon. A malformed/absent tz is treated as `+00:00`. One formatter per parse, not per line.

**Robustness.** Unknown headers are skipped; a truncated final group, a missing metadata field, a non-numeric line number, and empty output must all yield a well-formed array rather than trapping. Entries are placed by the header's final line number, so the array is sized by the highest line seen and gaps stay `nil`.

**`BlameShift`.** Signature: `static func updated(previous: [BlameLine?], previousLineStarts: [Int], newLineStarts: [Int], editedRange: NSRange, changeInLength: Int) -> [BlameLine?]`. It is pure arithmetic over line-start arrays — no `NSString`, no scanning — because the gutter already holds both arrays at the moment of the edit (`LineStartIndex.updated` produces the new one). This guarantees the invariant structurally: `result.count == newLineStarts.count`, always.

- Old touched line span, with `loc = editedRange.location` and `oldEnd = loc + editedRange.length - changeInLength` (the end of the replaced region in **pre-edit** coordinates):
  - `first` = index of the last `previousLineStarts <= loc`.
  - `last` = index of the last `previousLineStarts <= max(loc, oldEnd - 1)` — i.e. the line containing the **last character actually removed**, not the position just past it.
  - **Why `oldEnd - 1`, clamped up to `loc`.** `oldEnd` is an exclusive bound, so on a whole-line deletion it lands exactly on the *next* line's start and pulls an untouched line into the span. Concretely, with line starts `[0, 10, 20, 30]`, deleting line 1 entirely (`loc = 10`, removing 10 units, `oldEnd = 20`) would give `last = 2` under an `oldEnd` rule; the span then collapses to one line carrying old line 1's annotation, now sitting on old line **2**'s content — precisely the annotation-migration the invariant forbids. With `max(loc, oldEnd - 1) = 19` the span is `1…1`, contributes zero new lines, and old lines 2–3 pass through the untouched-suffix branch with their own annotations. The `max(loc, …)` clamp is what keeps a pure **insertion** correct (`oldEnd == loc`, so `oldEnd - 1` would otherwise reach back into the *previous* line and drag it into the span): there `last == first`, one line touched.
- Lines before `first` are kept verbatim; lines after `last` are kept verbatim (their content is untouched — only their index shifts by the line-count delta). Neither can migrate onto a foreign line.
- **The touched span: annotations survive only when the span's line count is unchanged.** The span's new length is derived from the arrays — `newSpanLength = newLineStarts.count - first - (previous.count - last - 1)`. When `newSpanLength == last - first + 1` the edit was **structure-preserving** inside the span (no line break added or removed there), so the span's old annotations are copied over position for position: an ordinary keystroke leaves the line's annotation in place, which is the deliberate, ticket-sanctioned inaccuracy the post-save recompute fixes. When the count differs — an Enter split, an insertion at a line start, a multi-line paste, a deletion joining two lines, a whole-line deletion (`newSpanLength == 0`, contributing nothing at all) — the **whole span becomes `nil`**.
- **Why not "the first touched line keeps its annotation".** That weaker rule looks harmless but hands a real annotation to a line the user just created: inserting at a line start, or pressing Enter at column 0, makes the *first* new line a brand-new empty line that would then be attributed to the previous line's commit. Tying survival to an unchanged line count makes it a structural property — an annotation survives only where the line's index within the span and the span's shape are both unchanged — at the cost of blanking a joined line's annotation, which the next save recomputes anyway. Blank is honest; a wrong author is not.
- Fallback: any inconsistent input (`previous.count != previousLineStarts.count`, a non-`0`-anchored array, an out-of-range edit, an empty line-start array, a `newSpanLength` that comes out negative) returns `[BlameLine?](repeating: nil, count: newLineStarts.count)` — honest "unknown", never a drifted array.

**Service seam.** `func blame(fileURL: URL) async throws -> [BlameLine?]`, defaulted to `[]` in the protocol extension. It takes an absolute file URL rather than the `(path:root:)` shape the rest of the protocol uses, and that deviation is deliberate: the caller here holds a workspace URL, not a repo-relative path, so `GitCLIService` runs git with the file's own directory as the working directory and lets git discover the repository — no `repositoryRoot` round-trip, and a file outside any repository simply exits non-zero. `GitCLIService` runs `git -c core.quotePath=false blame --porcelain -- <last path component>` and parses inside the (non-`@MainActor`, cooperative-pool) service method, so both the subprocess and the parse stay off the main thread.

**Recompute signal, and what the token promises.** A new per-file token in `WorkspaceModel`: `@Published public private(set) var diskRevisions: [UUID: Int]`, read through `diskRevision(for:)` (`0` for an unknown id), bumped by a private helper at **every** site that assigns `savedText` — `markSaved`, `save(for:)`, `saveAllDirty`, `saveAs`, `reloadFromDisk`, `reconcileSavedBaseline` — and dropped in `removeFile`. The rule is one sentence: *the on-disk content this buffer corresponds to changed*, which is exactly when a worktree blame goes stale. It covers save, autosave, Save As, post-revert reload, merge apply, and a branch checkout (which resyncs clean tabs through `reloadFromDisk` and edited ones through `reconcileSavedBaseline`). It is deliberately separate from `textReplacementRevisions` (which answers a different question — "drop this file's undo stack"). The **contract is "it changed", not "it went up by one"**, and the doc comment says so: consumers compare the token against the last value they saw (`BlameController`'s per-file last-seen revision, `Coordinator.noteExternalTextRevision`'s precedent), so the only observable properties are that an affected file's token differs afterwards and that no other file's does. Today's sites each assign `savedText` directly and bump once, but a mutator routed through another (a `save(for:)` that comes to delegate to `markSaved`, a `saveAllDirty` that reuses `save(for:)`) would bump twice and change nothing a consumer can see — so the tests pin the observable contract and never the arithmetic.

**Per-tab state = the toggle only.** The controller keeps `enabledFileIDs: Set<UUID>`; the annotation array lives in the ruler, for the displayed file only, and is (re)loaded whenever the shown file changes, its `diskRevision` changes, or its buffer is wholesale-replaced. A per-file annotation cache is deliberately not built: a reload is one short async subprocess, and reloading is also what keeps a tab correct after it was saved/checked-out while off screen.

**`enabledFileIDs` is deliberately *not* pruned on tab close — recorded, not overlooked.** The set only ever grows, by one `UUID` per tab the user turns annotate on for, and is dropped wholesale in `reset()` when the editor is torn down. Nothing prunes it on close, for three reasons stated together in its doc comment so a reader does not re-derive them as an oversight. (1) **It cannot go wrong.** A `UUID` is never reused — `WorkspaceModel.open(url:)` mints a fresh id even for a file that was previously open and closed — so a stale entry can never match a live tab and can never silently re-enable annotate for a different, or even for the *same*, file. Closing and reopening a file therefore starts with annotate off either way, whether the entry was pruned or not; pruning would change nothing a user can observe. (2) **The cost is a rounding error.** A `Set<UUID>` entry is 16 bytes, and the bound is "tabs annotated during this editor's lifetime", not "files in the project" — a heavy session is a few kilobytes. (3) **Pruning is not free in the way it looks.** The controller knows only the *displayed* file: it is handed a `fileID` per `sync`, never the open-tab list, so an intersection-based prune means threading `Set(model.openFiles.map(\.id))` from `ContentView` into `CodeEditorView` on every body evaluation — i.e. a fresh set allocated on every keystroke, since the editor binding republishes `openFiles` — plus a new parameter on the view, to reclaim bytes. That is the trade the repo's YAGNI convention rejects. This deliberately **differs from `WorkspaceModel.removeFile`**, which *does* prune `textReplacementRevisions` and (per Task 3) `diskRevisions`: those are `@Published` dictionaries in Core, living for the app's whole lifetime and already sitting inside the exact method that learns about the close, so pruning there is one line at the site that already has the information — the view-layer set has neither property. If a future feature ever gives the controller the open-tab list for its own reasons, pruning becomes the one-liner it is not today.

**Ordering around a buffer swap.** `updateNSView` must clear the ruler's annotations *before* `textView.string = text`, because that assignment posts a full-range edit notification that would otherwise run the shift over a whole-document replacement; the reload is kicked off after the swap.

**Two accepted inaccuracies, one family: the column describes the file *on disk*.** Blame is a worktree blame, so the annotations always answer "who last changed this line **in the file as git sees it**", and the buffer on screen can be ahead of that file in two distinct ways. Both are accepted, both self-heal, and both are documented together on `BlameController` so a reader meets them as one rule rather than two surprises.

- **A dirty, never-saved buffer.** Turning annotate on (or leaving it on) while the buffer holds unsaved edits blames the *last saved* bytes, and `BlameShift` only shifts annotations for edits made **after** the load — it cannot know about line insertions/deletions the buffer already carried when the load was issued. So on a dirty buffer the column can be **offset by whole lines until the next autosave**: the load returns an array laid out for the on-disk line numbering while the ruler indexes it by the buffer's. This is the same class of inaccuracy as load-vs-typing below, and in practice the window is short — autosave fires after `AutosaveController.idleDelay` (2 s of idle), on a tab switch, and on focus loss, and every one of those bumps `diskRevisions`, which triggers a recompute. The engineering reason not to "fix" it is that the only fixes are worse than the symptom: blaming a temp copy of the buffer through `git blame --contents -` would blame a file git has never seen (every unsaved line becomes uncommitted anyway, so the extra machinery buys a fraction of a second), and *saving on toggle* would make a read-only inspection command write the user's file. Blank-or-briefly-offset is the honest option.
- **Typing while a load is in flight.** The result describes the file as it was on disk at load time. On arrival it is padded/truncated to the current displayed line count and installed. The generation token guards against superseded loads and file switches, not against edits made while a load was in flight — those can likewise leave the column off by a line until the next save recomputes it.

**Column rendering, and where the width is measured.** The annotation column sits to the **left** of the numbers inside the same ruler and is drawn in the same pass, with the same `rulerFont` and `NSColor.secondaryLabelColor`. Labels are `"<author> <short date>"`, the author truncated to a 20-character cap with an ellipsis; the date is formatted per commit, not per line. The memo keyed by commit hash caches **label strings only** — no pixel widths — because a hash's label is font-independent while its rendered width is not: the shared editor font size changes at runtime (the Preferences Stepper and Cmd+scroll), and a width cached when the annotations were installed would leave the column sized for the *old* font with no signal to invalidate it. So the width is measured in `updateThickness()` at the **current** `rulerFont`, alongside the line-number measurement already done there, as the max over the memo's labels — which is what makes the existing `editorFontChanged() → updateThickness()` path re-derive the column for free, with nothing to invalidate. Measuring the whole memo per call was assumed cheap here — bounded by *distinct commits touching one file*, thought to be dozens — but a long-lived file has several hundred, which is milliseconds on the per-keystroke `lineMapDidChange` path; the implementation therefore memoizes the measured width **together with the font size it was measured at**, which keeps the runtime font change correct with nothing to invalidate (recorded in `CLAUDE.md` on `LineNumberRulerView`). `nil` and uncommitted lines draw nothing. With annotate off the column contributes 0 and the gutter is byte-identical to today.

**Context menu.** `LineNumberRulerView` overrides `menu(for:)` and returns a one-item menu — "Annotate with Git Blame" / "Close Annotations" depending on state — disabled when the file has no URL (an untitled buffer). The item calls an `onToggleAnnotate` closure, captured **weakly** on the coordinator for the retain-cycle reason documented on `onDuplicate`/`onCancelSearch`.

**Errors.** A blame failure (not a repository, file outside git, git missing) is swallowed by the controller: the column stays empty and the toggle simply produces nothing. No alerts, no beeps.
